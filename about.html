青藤图书室是怎么跑的

这一页说明系统的两种部署形态、当前你正在看的是哪一种，以及各自适合什么场景。 读者不需要读这一页也能正常借书，它是给评阅和运维看的。

一、两种部署形态

同一套页面与业务逻辑，本课题做了两种形态。两者的页面、样式、操作流程完全一致，区别只在数据存在哪里。

单机演示版当前站点 整个目录放进任意静态托管（GitHub Pages、校内 Web 服务器、甚至 U 盘）即可运行。 数据存在当前这台电脑或手机浏览器的 localStorage 里，换一台设备看到的是另一份数据。 适合演示、评审、单人练习，以及只有一台公用电脑的班级图书角。
共享部署版 使用 Node.js 内置模块与 SQLite 文件数据库，一条 node server/index.js 启动， 同一局域网内的电脑与手机访问同一个地址，看到的是同一份数据，账号密码与借阅记录跨设备共享。 适合真正需要多人同时预约、库存必须一致的系部图书室。
当前你访问的是单机演示版。 它不提供跨设备的账号同步：你在自己电脑上登录后产生的借阅记录，只保存在你自己这台机器的浏览器里。 这是纯前端方案固有的边界，本课题把它写进说明，不做模糊处理。

二、为什么先做单机演示版

课题开始时最紧迫的问题是“有没有一个能跑起来、看得见的东西”，而不是“能不能支撑几十人同时操作”。 在没有服务器预算、也没有运维人员的条件下，纯前端方案能在一周内把检索、详情、预约、借还、后台十个模块全部跑通， 让指导老师和同学先看到完整的业务流程。这一步做完，才有资格讨论后端该怎么接。

为了不给将来换后端留下返工，页面脚本从一开始就只通过一个统一的 api(路径, 参数) 入口取数，接口形状照搬 REST 的路径与方法。 单机版的这个入口后面接的是一张本地路由表；共享版的同一个入口接的是真实的 HTTP 请求。 两层之间的分界线只有一处，页面代码一行都不用改。

三、共享版是怎么解决多用户问题的

  • 账号与会话：登录成功后服务端签发 Cookie 会话，密码只保存随机盐与 SHA-256 摘要，不落明文。
  • 库存一致性：借出一册副本时先把该册状态改为已借出，再写借阅记录，同一个操作放在一个事务里完成。
  • 预约排队：归还时在同一事务内把该书最早一位排队读者的预约置为「已到书」并锁定那一册， 避免两个人同时拿到同一册。
  • 权限分级：读者、馆员、管理员三种角色，读者调用后台接口直接返回「没有该操作权限」。

四、数字形象看板

看板是本课题在“展示面”上的重点。它把馆藏规模、在架比例、外借与逾期、注册读者、累计借出、开放分类 六项指标做成一块可以挂在走廊屏幕上的画面，左侧是分类馆藏分布，中间是五个主题书架的藏书构成， 右侧是近十四天的借还柱状图，底部是借阅排行与借阅规则。

看板与借阅系统共用同一份数据，管理员在后台改动书目或办理借还之后，看板在三十秒内自动刷新。 对参观者来说，它提供的是“这个图书室此刻在发生什么”的直观印象； 对管理员来说，它是一块不需要操作、抬眼就能看的仪表。

五、五心主题书架

五个主题书架把馆藏按育人方向重新组织一遍：红心对应家国情怀与国情观察，仁心对应把使用门槛降下来， 恒心对应阅读的积累与持续，匠心对应精确到册的账，创心对应技术上的新做法。 检索页可以按书架筛选，看板可以看到每一架有多少种书。

这套对应关系不是给系统贴标签，而是让图书室的工作能跟系部的德育安排对上话： 书单由系部推荐、图书室落实采购与编目，借阅数据反过来为下一学期的主题阅读活动提供依据。

六、代码在哪里

单机演示版：library-static/，包含 9 个页面、9 份样式、16 份脚本与一份种子数据，零第三方依赖。

共享部署版：library/，服务端 9 个文件，使用 Node.js 内置的 node:http 与 node:sqlite，不安装任何 npm 包。
